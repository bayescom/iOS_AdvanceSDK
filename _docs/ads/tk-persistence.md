# TK 事件持久化与补发（V1）

现有 `AdvApiService reportAdDataWithEventType:...` 已接入 TK 队列，各广告类型沿用原来的调用入口。SDK 初始化时自动恢复未完成任务。一个最终 TK URL 对应一个独立任务，每次发送一个 GET；多个 URL 可以分别成功、失败和删除，不需要服务端增加批量接口。

## 重试限制

四项参数在 `AdvTKReportManager.m` 中集中定义。V1 使用以下默认值，尚未接入服务端动态配置：

| 参数 | 默认值 | 行为 |
| --- | --- | --- |
| `base_ms` | 5000 | 首次失败后等待 5 秒 |
| `cap_ms` | 120000 | 指数退避达到 120 秒后保持该间隔 |
| `max_retry` | 10 | 首次发送之外最多再重试 10 次，总请求次数最多 11 次 |
| `expire_ms` | 86400000 | 从事件产生起计算 24 小时，达到有效期后清理；重试不续期 |

第 `n` 次请求失败后的退避为 `min(cap_ms, base_ms × 2^(n - 1))`，10 次补发对应的等待时间为 `5、10、20、40、80、120、120、120、120、120` 秒。响应包含有效 `Retry-After` 时，取退避时间与服务端指定时间的较晚者；该服务端限流时间可以超过 120 秒，但不能延长事件有效期。没有随机抖动。

`attemptCount` 是发送前已持久化的尝试次数，包含首次发送。每次请求前先保存递增后的次数和下一次允许重试的时间；保存失败不发送，也不消耗重试次数。重启继续使用已保存的次数、有效期和时间。如果进程在最后一次请求途中退出，恢复后也不会获得额外额度。记录保存成功后、真正发出请求前退出，也会占用这次额度；若保存期间事件过期，则直接删除，不再发送。

## 调度和结果处理

- 新事件入队：在事件发生时替换时间、价格、错误、耗时等参数，持久化最终 URL，再开始发送。补发使用相同 URL，不重新生成事件参数。
- SDK 启动、回到前台、网络恢复、任务到期：检查所有符合发送时间的待发任务。重复唤醒不会绕过退避或重复发送在途任务。
- 每条请求在保存尝试记录前、保存成功后各复查一次有效期。批量落盘或本次写入跨过有效期时，任务进入本地删除流程，不启动 GET，也不阻塞后续正常任务。删除失败只重试删除。
- 并发上限为 3，每个任务同一时间只有一个请求，其余任务等待空位后发送。队列不设置任务数量上限，新事件入队和历史任务恢复均不会因积压数量而丢弃任务。
- 无网络错误且 HTTP 为 `2xx`：视为接收成功并删除本地任务，包括空响应和图片响应；不要求业务 JSON 回调。
- HTTP `408`、`429`、`5xx`、网络失败及其他未成功响应：按退避重试，受次数和有效期限制。
- HTTP 其他 `4xx` 或非法 URL：按不可重试处理并清理。
- 应用进入后台后停止启动新请求，继续处理已有请求结果和本地状态。不依赖后台定时器持续运行；恢复前台或重新启动时继续调度。

传输层使用独立的 `NSURLSession`，GET 请求绕过本地 HTTP 缓存，避免缓存的响应被当成本次上报确认。请求超时设置为 5 秒，完整资源传输最长为 15 秒。

## SQLite 持久化

`AdvTKEventStore` 直接使用 SQLite C API 实现数据库的打开、读写、事务及损坏数据隔离。

存储错误按 [SQLite 错误类别](https://www.sqlite.org/rescode.html) 区分：启动恢复时，只有 `SQLITE_CORRUPT`、`SQLITE_NOTADB` 及对应扩展错误码触发重建。锁、权限、磁盘满、I/O 等错误保留原库，每 5 秒重试。读操作区分 SQLite 的“读取完成”与“读取失败”，读取失败不能被当成空队列。

数据库文件为 `Library/Application Support/AdvanceSDK/TK/tk.sqlite`，排除系统备份，与普通广告缓存隔离。`TK` 为组件独占目录，不得放入其他模块的数据。全部存取在 TK 的同一串行队列执行，同一路径只使用一个存储实例。

任务表 `tk_events` 只有 `task_id` 和 `payload` 两列，以任务 ID 为主键，每条事件独占一行。`payload` 保存该事件的 JSON。保存、更新和删除只操作目标任务，无需读取或改写其他任务，也无需在存储层维护一份任务缓存。

每条任务保存 `taskId`、`appId`、最终 URL、事件类型、产生时间、失效时间、下次重试时间、已尝试次数。同样的 URL 若来自两次独立事件，会获得两个任务 ID，不按 URL 合并。

发生存储错误时，每 5 秒重试本地操作：

- 首次落盘失败：当前进程保留任务，不提前发出请求。
- 重试状态写入失败：等待写入恢复后再发送。
- 服务端已确认但删除失败：当前进程只重试删除，不再次上报。
- 启动恢复时打开、初始化或读取明确报数据库损坏：关闭连接，删除 TK 专用目录及数据库附属文件，在原路径创建新库，丢弃损坏库内的历史任务。
- 运行中保存或删除报数据库损坏：返回失败，沿用既有存储重试，未落盘任务不发送；当前进程不重建数据库，等下次进程启动初始化时处理。
- 任务 JSON、字段或任务 ID 校验失败：将该行的原始任务 ID、数据、原因及时间备份至 `tk_quarantine` 隔离表，再从任务表删除该行。两步在同一事务内完成；备份、删除或提交失败均回滚，并等待存储重试。隔离只影响坏记录，正常任务继续恢复，新任务也能正常落盘和发送。

隔离表不参与任务上报，重启不会重复隔离已处理的坏记录。无法解析的内容不能自动修复，原始字节保留供排查；V1 暂不自动清理隔离记录。

整库损坏只保留启动重建这一层兜底，不归档坏库，也不在运行中重建或重新导入内存任务。每次启动恢复调用最多重建一次；清理旧库或创建新库失败时返回错误，由既有的 5 秒存储重试继续处理，避免递归重建。新库创建、排除系统备份和表初始化沿用正常打开流程。重建期间新入队的任务沿用原有“先落盘后发送”流程。

`supplier.is*Repo` 标记只负责同一次渠道事件的入队去重，不能作为服务端已经确认的依据。队列独立负责后续补发。

## 交付语义与边界

这是有次数和期限限制的补发机制，不能承诺绝对不丢失或只送达一次。服务端已经接收但响应丢失、确认后本地删除失败且进程退出，都可能导致重复上报；要保证业务计数不重复，需要服务端按现有事件标识幂等。本实现不会擅自修改带签名的 TK URL 或增加请求参数。

入队到完成落盘之间存在异步窗口；磁盘不可写时，暂存在内存中的任务也无法跨进程恢复。SQLite 使用 WAL/NORMAL 持久化设置，因此不能保证设备断电等场景下的记录完整性。轻量坏库处理以恢复后续上报为目标，明确接受损坏库内历史任务的丢失。运行中发生数据库损坏时，本次进程中的待发任务可能无法持久化或补发，等下次启动重建后恢复新任务上报。

## 验证

在 macOS 项目根目录运行：

```sh
python3 Tests/run_tk_tests.py
```

测试运行实际 TK 模块，覆盖单条任务独立存储、更新和删除，数据库权限故障、初始化写锁、损坏及非损坏错误分类，坏文件头和真实 B-tree 页损坏的启动重建，旧库删除失败、新库创建失败后的重试，以及一次恢复调用最多重建一次。运行中入队写入、请求前状态写入和确认后删除发生真实 SQLite 损坏时，验证当前进程不重建、不提前发送或重发已确认任务，下次初始化重建后恢复新任务上报。

另覆盖坏 JSON/字段/任务 ID 的逐条隔离、备份或删除失败的事务回滚，落盘期间过期后不发送、先落盘后发送、并发及部分成功、HTTP 响应、Retry-After、退避上限、重启额度、删除失败、前后台切换、超过 2000 条完整入队和合并恢复。HTTP 由 `NSURLProtocol` 拦截，无需外网或实际等待两分钟。UIKit 使用测试替身，因此这些测试不替代真机生命周期和断网联调。

构建需要链接系统 `sqlite3`。TK 源文件包含在 Podspec 的现有通配路径中；CocoaPods 工程可执行 `pod install --no-repo-update` 更新生成的工程。
